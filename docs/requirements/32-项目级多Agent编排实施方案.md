# 项目级多 Agent 编排实施方案

日期：2026-10-16；2026-10-20 更新。状态：核心闭环在 0.16.1 实现；0.17.0 已补充真实协作画布、暂停后修改计划和手动/按组可选的重启自动恢复。费用预算、通用工具循环等仍不具备；下文保留设计与历次复核历史，不将方案全部视作已交付。当前实现和限制见 [0.17.0 验证](../verification-0.17.0.md)。

## 目标和参考

一个项目交办一个目标，由主 Agent 拆成多个有依赖的子任务，不同角色使用独立上下文和按角色配置的模型，完成后审阅、必要时返工，主任务统一交付。普通任务仍可使用单 Agent。

参考用户提供的 [V2EX 帖子](https://v2ex.com/t/1248818)：借鉴主协调者与专项执行者分工、按职责分配模型、验证后交付的机制。以下是基于 OpsBuddy 当前代码提出的工程方案，不照搬帖子中的组织、设备、模型型号或运营业务。保持 Go 后端、Windows 桌面、低资源与简洁入口。

## 实施前基础与缺口（10 月 16 日设计基线）

实际代码以 `internal/app/agents.go`、`tasks.go`、`workflows.go`、`src/AgentTeam.tsx` 及相应测试为准；启动开发时须重新核实。

- 已有真实子任务、独立上下文、最多 6 位成员、全局最多 3 个任务并发、单成员追加指令、取消传播、先审阅再汇总、项目隔离和持久化。
- 当前成员配置克隆主任务，不能分别选模型；编排主要是固定的“并行成员 → reviewer → 主汇总”，没有通用成员依赖与自动返工闭环。
- 当前非 worker 成员输出偏向 DOCX，开发协作不应让调研、审阅和状态交接都变成 Word 文件。
- 现有工作流已有画布和依赖运行机制。先评估复用，避免再造一套互不相通的调度器、角色库或图编辑器。

## 最小可用闭环

流程为：项目主目标 → 结构化计划 → 依赖调度与并行执行 → 审阅 → 有限返工 → 主任务验收与统一交付。

| 角色 | 职责 | 交付 |
| --- | --- | --- |
| 协调者 / planner | 拆解目标、声明输入输出与依赖、分配职责，处理冲突、最终验收 | 版本化执行计划、汇总 |
| 探查 / explorer | 读取明确引用的项目材料、识别现状和缺口 | 简短结构化事实与来源 |
| 执行 / worker | 完成一个可验收的办公或开发子任务，可按前端、后端、文案等命名 | 真实文件、代码或结果 |
| 审阅 / reviewer | 按计划验收标准检查真实交付，指出问题并关联责任任务 | 检查结论、返工项和证据 |

角色是本次执行职责，Skill 是按需读取的工作方法；不恢复独立专家库。角色可绑定已配置的模型连接和 Skills，也允许沿用主模型。开发本功能的定时任务使用 Astra / high，不代表应用内强制内置 Astra 或只能使用同一供应商。

### 计划与上下文

- 计划包含项目、主任务、计划版本、子任务 ID、角色、模型连接、目标、依赖、输入引用、交付类型、验收条件、失败策略。
- 主模型可以输出结构化计划；执行前用本地校验器拒绝未知节点、环、跨项目引用、不可用模型及超限计划。计划能力未具备时应显式报错，不用硬编码分工假装模型已规划。
- 用户选择协作模式并提交目标即按当前权限开始执行，计划和进度可见；提供手动调整计划入口，不强制每个普通子步骤重复确认。
- 子 Agent 只接收本任务指令、必要项目约束、用户指定材料及声明依赖的交付；不能把整个项目历史或其他项目会话一起塞入上下文。
- 成员模型配置、技能版本、计划与输入在运行时保存快照。密钥留在执行层，不写入计划、成员消息、日志或成果。

### 调度、模型和返工

- 优先复用当前任务队列和工作流依赖机制。同一计划支持顺序、并行和汇合；只有依赖满足才派发下游，界面状态来自真实持久化任务。
- 第一阶段默认最多 6 个子任务、最多 3 个并发、1 层委派、审阅返工最多 2 轮、单节点自动重试最多 1 次；限制在设置范围内可调，不允许无界递归。
- 每成员可选不同的已配置模型，分别解析连接和密钥，并展示请求与返回模型标识。不可用时明确失败，不擅自换供应商或降级成本地模板。
- 模型开销先统计实际返回的 token / 请求数与配置限额；没有供应商用量或价格时标为未知，不编造费用或预算精度。
- 审阅结果使用结构化 pass / rework / blocked 状态；返工只触发有关节点及受影响下游，已通过的独立分支和成果保留。
- 取消主任务后阻止后续派发，取消运行请求与返工；部分失败、全部失败和取消须区别显示。重开后标记中断，用户选择后才重新调用模型。

### 开发与办公交付

- 分析、计划、审阅优先作为会话内 Markdown / 结构化记录展示；用户明确要文档时才导出，不强制为每个角色生成 DOCX。
- 代码任务给每个成员明确文件职责。并行成员输出独立候选文件，最终集成者合并；同一路径冲突必须检测并说明，不允许后写覆盖先写。
- 最终代码按真实源码目录、文件树和可运行项目交付，支持前端与 Go 后端；ZIP 只作主动导出。生成服务后实际启动，在右侧打开预览和日志。
- Office / Markdown 等交付复用现有成果与版本管理，引用真实上游产出，保留原件，不生成虚假的“已完成”步骤。

## 桌面交互

项目任务输入区提供简洁的协作模式入口；一次任务仍对应主会话。主会话内展示计划摘要、成员角色与模型、依赖、当前状态、耗时、错误、交付链接和返工记录，可展开单成员会话、追加要求或停止整组。

复杂依赖可借用已有工作流画布查看，普通任务不要求先画图。避免另建企业组织、部门、数字员工管理台；不扩展本轮范围到社交平台运营、手机号、消息渠道或语音。

## 开发顺序与验收

1. 核对现有行为和测试，先完成数据契约及调度复用设计，补充字段与兼容迁移。
2. 闭环实现角色模型绑定、依赖执行、结构化审阅和有限返工，保持项目边界与旧会话兼容。
3. 接上简洁桌面进度视图与原有源码 / 文件预览，不重做全站 UI 或宠物。
4. 用可控模拟模型验证不同模型端点、依赖先后、真实并行、重试返工上限、取消后不再派发、项目隔离及凭据不外泄。
5. 桌面验证“资料分析 → 撰写 → 审阅 → 最终文件”和“前端 + Go 后端并行 → 集成 → 检查 → 启动预览”。前端按钮、Go 接口和最终文件都须真实可用，不能仅测试模型返回 HTTP 200。
6. 跑适当的 Go / vet / TypeScript 检查和最终 EXE 自检，记录已实现、缺口与未验证项，更新使用指南、实现状态及验收记录。
